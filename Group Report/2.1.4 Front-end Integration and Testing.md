### 2.1.4 Front-end Integration and Testing

The front end and Express API share an origin. A barrier report moves from browser validation to `POST /api/barriers`, is stored in MySQL and becomes visible only after review (Figure 8). Mapper answers are queued locally when offline, whereas failed barrier reports require users to retry.

Static checks alone did not establish that these journeys worked: all 28 original checks passed while several interaction defects remained. In an isolated AI-assisted run using Node 22, MariaDB 10.11 and headless Chrome 153, the revised code passed 37 static checks, six existing API tests, five new reporting regression tests and 37 browser checks (Table 3). These results have not yet been repeated by the student team or on MySQL 8.4.

Browser testing exposed an Escape-key problem: while selecting a map point, the handler reopened the dialog before the browser applied Escape's default action, closing it again and losing the note. Adding `preventDefault()` preserved the input. The confirmation toast also ignored its requested duration, appearing for 2.6 rather than 5.2 seconds; it now accepts a duration parameter. Network failures now retain the form and display a readable message.

These findings show why testing connected user journeys matters beyond checking individual functions. Mobile devices, screen readers and camera permissions remain untested, and reporting tests do not yet run automatically on pull requests.
